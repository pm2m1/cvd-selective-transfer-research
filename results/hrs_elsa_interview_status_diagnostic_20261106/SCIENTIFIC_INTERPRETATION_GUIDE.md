# Scientific interpretation and protected outputs

## What this diagnostic can establish

After a genuinely authorized execution, private matrices can distinguish explicit zero, missing/tagged missing and invalid participation; explicit personal/partial/proxy/institutional outcomes; proxy inference through `askpx`; absent Core records; and unmatched/invalid linkage. It reproduces the precise frozen response/interview predicate, not an endpoint model.

A known-zero versus explicit responding outcome is a **recorded disagreement**. It is not by itself proof of an implementation defect, wrong linkage, a particular survey route or which release is authoritative. A missing participation flag is unavailable evidence, not an observed zero. A proxy fallback is a decoder route, not independent proof that the participant was interviewed or eligible. More than one mechanism may occur.

The source registration identity guarantees only the qualified local archive/member bindings it originally recorded. It does not independently authenticate publisher origin or the acquired archive edition. A named dictionary/revision and exact byte hash do not ensure every index/Core status is semantically aligned. This task does not reopen broad provenance investigations or invent an edition.

## Private report files

| File | Contents / status |
|---|---|
| `operation_started.private.json` | Original runtime consumed-before-processing marker |
| `runtime.private.log` | Protected redirected runtime output; never upload unrestricted context |
| `input_validation.private.json` | Aggregate missing/invalid/duplicate linkage issues, no keys/rows |
| `status_diagnostic.private.json` | Per-wave participation/Core/basis matrix, raw-state frequency tokens, zero-versus-missing rejection summaries, first category, coverage, unresolved interpretation and source/code bindings |
| `diagnostic_integrity.private.json` | Successful diagnostic output digests and actual runtime versions |
| `operational_summary.json` | Identical static operational statement across successful findings; no counts, combinations or empirical verdict |
| `completion.private.json` | Completed or permanently failed/interrupted consumed result |

The report deliberately does not export participant records, IDs, linkage keys, interview/diagnosis dates or arbitrary source text. Detailed status frequencies can still expose small groups. They remain restricted even when names and IDs are absent. A first-category summary is also private. Do not upload any detailed report merely because it contains aggregates.

Successful operational summary content is static:

```json
{
  "status": "PRIVATE_STATUS_DIAGNOSTIC_WRITTEN_DISCLOSURE_REVIEW_REQUIRED",
  "scope": "STATUS_ONLY",
  "eligibility_changed": false,
  "models_or_events_computed": false,
  "clinical_or_scientific_acceptance": "NOT_GRANTED",
  "attempt_consumed": true
}
```

This file can support operational discussion without exposing an empirical class. Sharing is still subject to applicable institutional/provider rules. Failed operations may retain a partial input diagnostic or a status matrix without a successful operational summary. Never label such retained evidence as a completed accepted analysis.

## Action classes

**A — Observability only.** Separate issue codes, clearer missingness/decoder-basis reports, unchanged rejection decisions. This diagnostic is category A: it does not amend the count protocol. The earlier isolated error-code proposal remains uninstalled.

**B — Demonstrated implementation correction.** Requires a public specification violation supported by exact code, documentary evidence and regression reproduction. A private disagreement alone is insufficient. No such eligibility-changing defect is established or automatically corrected here. Any supported change needs a new reviewed code release and fresh bindings.

**C — Scientific protocol amendment.** Includes Core-over-harmonized precedence, treating ambiguous/missing evidence as an interview, replacing global rejection with exclusions, quarantining person-waves, changing history references or disease-free eligibility. Such changes require a prospective, evidence-backed amendment and source/endpoint impact tests. The diagnostic never implements them.

## What must be resolved before corrected counts

1. Identify whether the affected combinations are explicit-zero disagreements, unavailable flags, proxy fallback, incompatible codes, linkage problems or a mixture.
2. Establish the relevant release-specific joint-field semantics and original input equivalence. The future diagnostic must use the same registered source snapshots intended for the failed operation; the operator must establish that equivalence from permitted metadata. This tool never opens old count receipts, authorization or outputs to infer it.
3. For any proposed remedy, establish why it preserves credible history/interval references, missingness, proxy/Exit/death rules and selection accounting. Do not choose the interpretation yielding more eligible people or events.
4. Retain genuine contradictions as blocked unless a scientifically justified prospective policy says otherwise. Do not silently drop a visit and let an unobserved interval become a negative history.
5. Publish the minimal justified correction/amendment, verify exact new sources/config/protocol/runtime, and obtain a new independent count authorization and output destination. The diagnostic authorization cannot be reused.

The consumed count attempt stays `FAILED_NO_RETRY`. No source-registry artifact, previous model result or count eligibility rule is changed. This diagnostic and its synthetic tests establish neither empirical event support nor permission to start Phase 2B.
