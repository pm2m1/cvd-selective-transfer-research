# Safety, scope and preservation

## Boundaries enforced by code

- CLI and documented bind/check entrypoints require the existing independent-terminal policy: no agent/CI environment markers and a TTY. No guard is removed or spoofed. Synthetic tests mock this boundary only for invented temporary records; child-process tests exercise the genuine guard.
- Absolute paths, no `..`, no symlinked components, owner identity, exactly0600 JSON files, and owner-only directories within the selected private root are required. The new review configuration cannot be inside the helper, frozen tool tree or any of the three historical run directories.
- Default discovery is nonrecursive. It lists only the two named operation directories and considers bounded authorization/configuration JSON filename families. Roles then require purpose/schema/config-hash evidence. Multiple authorizations refuse rather than rank or choose. Exact output files come from recorded output bindings; registration comes from the recorded source-registration descriptor within the named registration run.
- The optional explicit map is a private reviewed allowlist. Exactly ten distinct role paths are required. Duplicate JSON keys, duplicate paths, missing/extra roles, invalid SHA256 values, non-JSON files, incompatible metadata and public-tool mismatches stop before configuration writes.
- The pinned original release is verified in place. Its unmodified metadata validator checks historical integrity links and source-descriptor equivalence. No original review execution, classifier, scientific worksheet generator, raw loader, count engine or model is invoked. No Stata/ZIP/NPZ/checkpoint path is opened or hashed. Source paths contained in JSON remain metadata values only.
- Only `private_root` and `evidence` change. Public pin, schema, flags and unresolved permission/isolation/scope remain byte-equivalent at the JSON-value level. Backup preserves the exact original file bytes. No declaration becomes approved automatically.
- The review-run directory must be pristine before binding. Backup/staging/binding-record files use exclusive creation and0600 modes. Files and containing directory are fsynced; final replacement is atomic. The configuration's original bytes/inode and all selected metadata hashes are rechecked before replacement. A binding record is created only after replacement verification. Interrupted or failed preparations are retained and cannot be silently retried.
- Read-only check verifies backup/record/core bindings and current evidence hashes. It permits only the original unresolved declarations or the exact declarations independently recorded later. It does not accept arbitrary partial approvals or modify a record. An existing review authorization/output or unrelated run artifact blocks preparation/check.

## What the code does not prove

File permissions, hashes, record schemas, scope literals and generic PASS messages do not establish licences, institutional/provider approval, isolation from AI/indexers, authentic distributor provenance, scientific equivalence, source-byte freshness, reviewer competence or an adopted interpretation. Local metadata-access permission must exist **before** binding. Distinct review permission and the original interactive authorization are later requirements. Unknown scientific findings remain unknown.

The helper reads/hashes the selected JSON metadata and its own mechanical configuration/backup/record, plus pinned public code. Controlled discovery may read additional approved candidate configuration JSONs while matching the recorded config hash; use the explicit map when permission does not cover that candidate discovery. It never enumerates other research areas, follows clinical source descriptors, contacts a network or prints paths, hashes, frequencies or arbitrary exception context.

## Preservation evidence

PRESERVATION_BINDINGS.json records28 original public review files, including its release manifest, verified before work. The unchanged public reference copy under tests exists only for reproducible synthetic interface checks. It is not installed into or merged with the actual private tool tree. Tests dynamically generate explicitly invented metadata; no real historical configuration, authorization, receipt or report is packaged.

No actual private directory, configuration, status matrix, authorization or source was accessed by Codex. No real binding, offline review, count, model training or final evaluation occurred. No frozen experiment or previous release was modified. No Git operation or upload was performed.
